## 5. Privacy

**Legal context (Assumption — to be confirmed by legal/owner, not established in code):** customers are mainly in the Gulf (Saudi PDPL, UAE PDPL), with some EU/UK visitors (GDPR, ePrivacy). The code already treats PDPL as applicable: WhatsApp consent is separate "under the PDPL and under Meta's policy" (**Fact** — `40-customer.prisma`, `Customer.whatsappOptInAt` comment).

**Consent.**

- There is **no cookie/consent banner** in the storefront today (**Fact** — no consent component under `apps/storefront/src`).
- First-party, aggregate-only measurement with no cross-site identifier and no transfer to a third party is the configuration most likely to be usable without a banner under ePrivacy's analytics exemptions as interpreted by several EU regulators (e.g. CNIL) and under PDPL's legitimate-interest basis. **Assumption** — legal review required.
- Anything that sends identifiers to Google, Meta or Pinterest (GA4 MP, Meta CAPI) is advertising/profiling: it needs **opt-in consent** for EU visitors and a disclosed cross-border transfer under PDPL. Existing marketing consent (`Customer.marketingOptInAt`) covers email campaigns, not ad-platform sharing — it must not be reused for that.

**What is PII here, and the rule for each.**

| Data                                                                             | PII?                                                                                               | Rule in analytics                                                                                                                                                                             |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email, name, phone, WhatsApp number, billing address, VAT no., `activationEmail` | Yes                                                                                                | **Never** in an event. Join to orders by `order_id` inside the database if ever needed.                                                                                                       |
| IP address                                                                       | Yes                                                                                                | Not stored on events. Used only transiently to derive coarse country, then dropped. (`Order.ip` exists for fraud; analytics must not read it.)                                                |
| Full user agent                                                                  | Quasi-identifier                                                                                   | Reduced to `device_class` + `is_bot` at ingest; raw UA not stored.                                                                                                                            |
| `visitor_id` cookie                                                              | Pseudonymous identifier                                                                            | Random, first-party, httpOnly, rotated at most every 30 days, never shared off-site. If the owner wants no-banner operation, use a daily-rotating hash (Plausible-style) instead of a cookie. |
| `cart_id`, `order_id`, `customer_id`                                             | Pseudonymous (linkable in DB)                                                                      | Allowed on server events; never sent to a third party.                                                                                                                                        |
| Coupon code strings                                                              | Can identify a person (single-use, customer-bound codes — `CartRecoveryEvent.promotionId` comment) | Record `promotion_id` / type, not the string.                                                                                                                                                 |
| Search query text                                                                | May contain an email or key pasted by mistake                                                      | Store only if it matches no email/key-like pattern; else store length only.                                                                                                                   |
| Licence keys, key ids, credentials, order-note text                              | Secret                                                                                             | **Never.** Vault ids stay in `OrderItem.assignedKeyIds`; no event references them (CLAUDE.md rule 1, 4).                                                                                      |
| Full referrer URL, query string                                                  | May carry tokens (recovery links, login links)                                                     | Host only for referrer; path without query for `page_viewed`; UTM keys allow-listed.                                                                                                          |

**Retention (proposal — owner decision).** Raw events: 13 months (enables year-on-year), then aggregate and delete. `web_vital` raw: 90 days. Aggregates: indefinite (no personal data). A sweep would enforce it; none exists today (**Fact** — no retention/purge job for analytics data because there is no analytics data).

**Data subject requests.** Because events carry no email, a deletion request is satisfied by deleting the customer and nulling `customer_id` on their events; cart/order-linked events become anonymous. **Assumption:** the account-deletion path (`Customer.deletedAt`) would need to cover the event table.

**Bots.** The shop renders per request, so server-side view counting sees crawlers. `is_bot` must be set at ingest and bots excluded from funnel figures.

## 7. Recommendation — **needs owner decision**

**Proposed (not approved):**

1. **Now, no new vendor:** Option **A + A′ + H.**
   - Build commerce events 10–21 as SQL views over the existing tables. There is nothing new to collect, only queries.
   - Add a small `analytics_event` table and log `session_started`, `page_viewed`, `product_viewed` and `whatsapp_clicked` from the storefront server (A′) and a same-origin `/go/whatsapp` redirect, plus `cart_item_added` and `coupon_applied` in the API.
   - Pull Search Console via its API for the SEO KPIs.
   - Zero client-side bytes, zero CSP changes, zero third parties, and no consent banner is needed (**Assumption**, to be confirmed by legal).
   - Delivers every §15 KPI plus the funnel.
2. **Later, only if the owner wants a ready-made traffic UI:** add **D (self-hosted Umami, same origin).** Treat it as an L4 change: it touches CSP handling and the script budget.
3. **Only when paid acquisition starts:** add **B (GA4 Measurement Protocol)** and **G (Meta CAPI)**. Both run server-side, fire on `purchase_completed`, and are gated on opt-in consent. That needs a consent mechanism, which does not exist today.
4. **Do not use** C (gtag.js) or F without a proxy. They break the zero-third-party budget the plan itself sets.

**Decisions the owner must make:**

- **D1.** Accept first-party-only measurement for launch, i.e. no Google Analytics UI at launch, or require GA4. If GA4 is required, choose server-side MP (B) or the client tag (C, which breaks the budget).
- **D2.** Whether a consent banner will exist at all. It is required before any ad-platform sharing (B/G) for EU visitors.
- **D3.** Raw-event retention period (proposed 13 months) and the visitor-identifier choice: rotating cookie or cookieless daily hash.
- **D4.** Whether a self-hosted Umami (D) is worth the extra container and one more script.

Legal confirmation of the consent assumptions in §5 is a prerequisite for D1–D2. This plan does not provide it.
