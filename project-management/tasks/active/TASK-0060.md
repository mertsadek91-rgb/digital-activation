**What is not covered anywhere:**

2. Delivery **latency.** This is the Release 1 acceptance: under 60 s.
3. The **vault key state** after delivery (AVAILABLE → DELIVERED) and the **customer portal reveal.** No test signs in as a customer and reads the key back.
4. The **vault-short failure path.** Stock is sold but the vault has no key, so the line should go to `MANUAL_QUEUE`.
5. Locale on the order and its mails (ar and en).
6. The **browser layer**: the storefront checkout UI, Stripe Elements and the RTL snapshot. No Playwright exists in the repo (no `playwright` in any `package.json`).

### 1. Tier A — API end-to-end: card order to licence delivered (new int suite)

**File to create:** `apps/api/src/integration/card-to-licence.int.test.ts`.

#### Setup

- Set the Stripe test values in `vi.hoisted`, before AppModule is imported. This is the same pattern as the FP suite's config block (`final-processor.int.test.ts:30-43`), because `env.ts:43-70` blanks them:
  - `STRIPE_SECRET_KEY='sk_test_integration_dummy'`, which is needed only so `StripeService.stripe()` (`stripe.service.ts:30-38`) can build a client for `webhooks.constructEvent`
  - `STRIPE_WEBHOOK_SECRET='whsec_integration_' + 'x'.repeat(24)`
  - `STRIPE_PUBLISHABLE_KEY='pk_test_integration_dummy'`

  These are dummy strings, not Stripe-issued keys. Nothing leaves the process.

- Stub `fetch` to throw, exactly as `final-processor.int.test.ts:79-85` does. Then any accidental Stripe API call fails loudly instead of reaching the network.
- Call `harness = await bootApp()` (`harness.ts:53`), then **restore the real signature check** with `vi.mocked(stripe.constructEvent).mockRestore()`. Keep the `riskLevelOf` stub (`harness.ts:74`): `latest_charge: null` already makes it return null without a network call, but the stub guards against regressions.
  - Cleaner alternative (preferred, a small harness change): `bootApp({ verifyStripeSignatures: true })`, which skips the `constructEvent` spy.
- Stub `StripeService.intentFor` with `vi.spyOn(...).mockResolvedValue({ id: 'pi_it_<run>', clientSecret: 'pi_it_<run>_secret_x' })`. Then `POST /v1/orders/:number/pay {provider:'STRIPE'}` runs for real (`checkout.controller.ts:138-188`): the amount from the order row, `recordOpenIntent`, and the session shape. It never calls Stripe. Check the exact return type of `intentFor` (`stripe.service.ts:72`) before stubbing.
- `catalogue = await seedCatalogue(harness)` (`harness.ts:139-220`): one FROM_STOCK variant with 3 keys imported through the vault's own path (`FulfillmentService.importKeys`), plus one ON_DEMAND variant.
- For the failure path, add one more FROM_STOCK variant in the suite, under the run's unique slug, with **no keys imported**, and set its `InventoryLevel.onHand = 1` directly through `harness.db` (public schema). This reproduces the shelf/vault drift that `fulfillment.service.ts:248-260` handles. It never touches the vault schema from outside `apps/api/src/vault/`.

#### Signing a Stripe webhook locally (no Stripe account, no CLI)

Use the SDK's own test helper. It produces the exact `t=…,v1=…` header that `webhooks.constructEvent` verifies:

```ts
import Stripe from 'stripe';
const sdk = new Stripe('sk_test_integration_dummy');
const payload = JSON.stringify(event); // the exact bytes posted
const header = sdk.webhooks.generateTestHeaderString({
  payload,
  secret: process.env.STRIPE_WEBHOOK_SECRET!,
});
await harness.app.inject({
  method: 'POST',
  url: '/v1/webhooks/stripe',
  headers: { 'content-type': 'application/json', 'stripe-signature': header },
  payload,
});
```

Build the event with the existing `paymentSucceeded()` (`harness.ts:229-250`), passing the `intentId` from the stubbed `intentFor`. Add a `signedDeliver(harness, event, secret?)` helper to `harness.ts`, next to `deliver()` (`harness.ts:277-288`), so later suites can reuse it.

For a manual run against a live local API, the alternative is `stripe listen --forward-to localhost:4000/v1/webhooks/stripe` plus `stripe trigger payment_intent.succeeded`. That needs a Stripe test-mode account and the CLI, so it belongs to Tier B only.

#### Scenarios and assertions

Run them in order with a shared catalogue. `run` is unique per execution, so nothing is truncated.

**A1 — card order to licence delivered, ar (happy path + latency)**

1. `shopper(harness)` (`harness.ts:97`) → `POST /v1/cart/items {variantId: stocked, qty: 1}` → 201.
2. `POST /v1/checkout?locale=ar&currency=USD {email: a1-<run>@example.test}` → 201. Parse it with `checkoutSchema`. Assert the order is `PENDING_PAYMENT`.
3. `POST /v1/orders/<n>/pay {provider:'STRIPE'}` → 201. The body parses as `paymentSessionSchema`, `provider === 'STRIPE'` and the amount equals `CheckoutService.chargeForNumber(n)` (`checkout.service.ts:610`).
4. Set `t0 = Date.now()`, then post the **signed** `payment_intent.succeeded` for the charge → `{status:201, body:{received:true}}`.
5. DB assertions:
   - `order.status === FULFILLED`, `paidAt` and `fulfilledAt` are set, and `order.locale` is ar.
   - Exactly 1 `payment` row: `providerRef = intentId`, provider STRIPE, state SUCCEEDED.
   - The `orderStatusEvent` rows read PENDING_PAYMENT → PAID → FULFILLED (verify the model and field names against `transitionOrder`).
   - `webhookEvent` (provider STRIPE, eventId): `processedAt` set, `attempts = 1`, `error` null. Also assert `signatureVerified` if the controller sets it. Check `checkout.service.ts` `beginWebhook`: if it never sets it, record that as a finding, not a failure.
   - Each `orderItem` is `DELIVERED`, with `deliveredAt` set and one `assignedKeyIds` entry.
   - `inventoryLevel.onHand` goes down by 1.
6. **Vault key status**, through the public service API and never `vaultPrisma`: `harness.get(FulfillmentService).keysForOrder(n)` (`fulfillment.service.ts:1224`) → every key `state === 'DELIVERED'`, with `deliveredAt` set.
7. **Email captured:**
   - `notificationLog` has `template='licence.delivered'`, `deliveredAt` not null, `payload.orderNumber = n`, `toAddress` equal to the order email and `locale = AR`. The query is the same as `checkout-payment.int.test.ts:75-82`.
   - Plus exactly one `order.received` row (`fulfillment.service.ts:992`).
   - Never open the files the capture transport writes, and never assert on key plaintext from mail.
8. **Latency:** `max(item.deliveredAt) - t0 < 60_000` ms. Inside one process this will be well under a second. The assertion protects the requirement, not the number. Also log the measured value as test output for the evidence record.

**A2 — the same in en.** Repeat A1 with `?locale=en`. Assert `order.locale = EN` and that the `licence.delivered` row has `locale = EN`. Use a different email address.

**A3 — customer portal shows the key (closes "key visible in the portal" at API level)**

1. Sign in as the A1 customer without reading any mail. Insert a `customerLoginToken` for the customer: `tokenHash = sha256hex(token)`, `expiresAt` +15 min. The hash is the same as `AccountService.hash` (`account.service.ts:79-80`).
2. Then call `POST /v1/account/session {token}` (`account.controller.ts:114`) and take the `da_customer` cookie. This tests the real exchange (`account.service.ts:169`).
3. Check `GET /v1/account/licences`: the A1 line has `state DELIVERED` and `hasSecret: true`.
4. Check `POST /v1/account/licences/<orderItemId>/reveal`: 2xx, one secret of the variant's credential kind. Assert only that it is non-empty and matches the imported test pattern `/^IT-<run>-KEY-/`. **Never print it.** These are synthetic keys from `seedCatalogue`, not real licences, but the habit matters.
5. Assert that a `KeyAccessLog` (or equivalent) reveal row was written, through whatever public surface exists. If that is only readable via the vault client, skip it here and note it.
6. Negative check: a second customer's session gets 404 on the same reveal. This verifies the "a check, not a filter" claim in `account.service.ts:355-360`.

**A4 — idempotency on replay**

1. Post the **identical** payload and header from A1 again → 201 `{received:true}`.
2. Assert:
   - `webhookEvent.attempts === 2` and `processedAt` is unchanged.
   - Still 1 `payment` row.
   - Still 1 `licence.delivered` and 1 `order.received` for the order.
   - `assignedKeyIds` unchanged.
   - `salesCount` and `onHand` unchanged.
   - No new `orderStatusEvent` rows.
3. **Re-signed replay:** the same event id with a fresh timestamp header, which is what Stripe's own retry looks like. Same assertions.
4. **Concurrent duplicate:** `Promise.all` of two deliveries of a _new_ paid event. Exactly one set of keys and mails. This exercises the compare-and-set in `onOrderPaid` (`fulfillment.service.ts:262-279`).

**A5 — signature rejection**

1. A wrong secret, a tampered payload (one byte changed after signing) and a missing header each get 400 (`stripe.service.ts:168-185`).
2. For each, assert: no `webhookEvent` row for that event id, and the order is still `PENDING_PAYMENT`.
3. A timestamp older than the SDK tolerance (300 s), generated with `generateTestHeaderString({ timestamp })`, also gets 400.

**A6 — failure path: no stock in the vault → queue**

1. Cart, checkout and pay for the drift variant (onHand 1, vault 0). Post the signed success event → 201. The webhook must not fail, because the money is taken.
2. Assert:
   - `order.status === PAID`. It is not FULFILLED and not FULFILLING, because no line is delivered.
   - The line is `fulfillmentState = MANUAL_QUEUE` with empty `assignedKeyIds`.
   - `order.received` was sent once and `licence.delivered` was not sent.
   - `FulfillmentService.queue({limit:50, includeDone:false})` contains the line.
   - `queueSummary().waiting >= 1`.
3. **Notify:** today the only signal is `logger.warn` (`fulfillment.service.ts:252-254`). There is no staff email or alert row. The test should assert what exists (queue membership) and record the missing staff notification as a finding for a separate BUG/OPP. It must not invent an expectation the code does not implement.
4. Optional recovery: import one key for the variant (`importKeys`), then deliver through the staff path (`deliverAssigned` or `fulfilManually`, `fulfillment.service.ts:576/696`, with a test staff actor and a fresh `totpAt`). Assert DELIVERED and one `licence.delivered`.

**A7 — kill switch (cheap, high value).** With `process.env.AUTO_DELIVERY='off'` set for one scenario (read at call time, `fulfillment.service.ts:98`), a paid stocked order leaves its line `AUTO_ASSIGNED`. The key state should be ASSIGNED, not DELIVERED, and no `licence.delivered` row is written. Restore the variable in `finally`.

### 2. Infrastructure: what exists and what is missing

- **CI already has a disposable Postgres.** In the `.github/workflows/ci.yml` job `schema`, a `postgres:18-alpine` service container runs migrations and the seed, then `pnpm --filter @da/api test:int` with `TEST_DATABASE_URL=postgresql://da:ci@localhost:5432/da_main`. A new `*.int.test.ts` file is picked up automatically (`vitest.int.config.ts` include `src/**/*.int.test.ts`). **Tier A needs no new CI infrastructure, no secrets and no owner-provisioned database to run in CI.**
- **What is missing is a local disposable Postgres.** There is no local Docker, and Postgres is remote. The `.env` database is the live staging database and must never be used: `guard.ts:10-24` refuses a non-local URL unless its name contains "test", or unless `ALLOW_REMOTE_TEST_DATABASE=1` is set. Options for running it before pushing:
  1. **CI only.** Push a branch and read the `schema` job. Zero cost and zero risk. It is slow feedback (one CI round per iteration), but it is enough for Tier A. **Recommended default.**
  2. **Neon branch / free Neon project** named `da_test_*`. Fast to create and throw away. Postgres 18 availability must be checked, because CI pins 18 to match Coolify. It needs an account owned by the owner, and the URL is a credential that must never land in the transcript.
  3. **A throwaway Coolify Postgres resource** on the staging host, with the database name `da_test`. It matches the production major. It shares a host with live staging, so a mistyped URL is one character from the live database. It needs an owner-approved task, and it must be deleted afterwards.
  4. **Local Postgres 18 without Docker** (Windows installer or `pg_ctl` from the zip) on `localhost:55432`. The guard accepts it with no override, and it has no shared-host risk. It needs a one-off install on the dev machine.

  Options 2-4 are each an owner decision (section 7).

- **Capture-transport side effect:** `MAIL_TRANSPORT=capture` writes rendered messages to `<repo-root>/.cache/mail` (`mail.service.ts:242`, `process.cwd()/../../.cache/mail`). In CI and in a worktree that is harmless. In the **main checkout**, `.cache/` is the read-only legacy input (CLAUDE.md rule 2), so a local run from the main checkout would write test mails, including synthetic key plaintext, into it. **Run local int tests only from a worktree.** Separately, consider a `MAIL_CAPTURE_DIR` override (a code change, needs its own task).

**The card step has two designs. This choice is an owner decision:**

- **B-real:** real Stripe **test mode**. The storefront's `card-payment.tsx` mounts Stripe Elements. The test types `4242 4242 4242 4242` into the Stripe iframe. The webhook reaches the local API through `stripe listen --forward-to` (Stripe CLI in CI) or a Stripe test-mode webhook endpoint. This needs:
  - Stripe **test** keys (`sk_test_…`, `pk_test_…`, and `whsec_…` from `stripe listen`) as GitHub Actions secrets
  - outbound network from the runner to Stripe

  It is the only variant that proves the Elements integration. It is flaky by nature (third-party iframe, network), so give it retries and run it on `main` or nightly rather than on every PR.

- **B-stub:** intercept `POST /v1/orders/*/pay` and the Stripe JS with Playwright `route()`. Fake the confirmation, then post a locally signed webhook (the section 1 helper) from the test. It is deterministic and needs no secrets. It proves the UI, the redirect, the order page, the portal and RTL, but **not** Stripe Elements.
- Recommended: B-stub on every PR, plus B-real on a schedule once the owner provides test keys.

**The provider question must be answered first.** The storefront offers `FINAL_PROCESSOR` methods (`stripe_card` via the processor, `product-trust.tsx:122` lists Visa/Mastercard under FINAL_PROCESSOR) beside direct `STRIPE`. Which provider _is_ "the card path" for Release 1 on staging and production decides whether Tier B drives Stripe Elements or the Final Processor redirect. The Final Processor has no public test-mode iframe to drive, so B-stub would be the only option for it.
