### 4. Proposed delivery-latency target (for the owner to confirm)

Today's code alerts on **any single** line past its promise in the last hour, so
one slow send keeps the alert red for up to an hour, while the plan's goal is a
percentage ("98 % under 60 s"). Proposed split between target and alerts:

- **Target (SLO):** stocked lines - p95 paid-to-delivered <= 60 s and >= 98 %
  delivered within 60 s, measured daily. Supplier/manual lines - within their own
  `deliverySlaSeconds` as shown on the product page.
- **Alert thresholds derived from it:**
  1. **Page now:** any paid stocked line still waiting > 5 min (past the stranded
     sweep's grace, the customer has nothing), or any line waiting past its own
     promise. This is the "customer is waiting" alert.
  2. **Page now:** `/health/ready` fails 2 consecutive checks (1-min interval, ~2 min).
  3. **Page now:** `/health/sweeps` fails 2 consecutive checks.
  4. **Warn, no page (daily summary):** stocked p95 over the last hour > 60 s, or
     any line delivered late.
  5. **Warn:** more than 5 new error-reporter events per hour, or any new issue in
     checkout, payment or fulfillment routes.
- Separating 1 from 4 needs a small code change in `apps/api/src/health/ops-checks.ts`
  (split "waiting" from "delivered late", add a p95 threshold). That file is not in
  this task's `affected_files`, so it needs a claim change before implementation.
