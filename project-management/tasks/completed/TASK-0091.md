# TASK-0091 — Order detail page: customer, payment, delivery, keys, notes and customer messaging actions in the admin

## Objective

The owner asked for a real order page: open an order and see everything about
it — the customer, the order, the payment, the delivery and the keys, the
notes — and act on it from one place, including writing to the customer
(payment received, review request, renewal reminder, a discount offer, a
free-form message). Modelled on the MediCore template's record page.

## Acceptance criteria

1. `/orders/[number]` renders the order in Arabic (RTL) and English, light
   and dark, at 1440/1024/768/390/360, with a customer card, an order-facts
   card and five tabs: overview, lines & delivery, payment, messages, notes.
2. `GET /v1/admin/orders/:number` carries `customer`, `billing`, `amounts`
   and `client`, and each line carries `unitPrice`, `credentialKind` and
   `expiresAt` (`packages/contracts/src/admin.ts`, `orders.service.ts`).
3. `POST /v1/admin/orders/:number/messages` (OWNER/ADMIN/SUPPORT, 20/min)
   sends one of `payment_received | review_request | renewal_reminder | offer
| custom` to the order's own address and nowhere else; every attempt is in
   `NotificationLog` with `orderNumber` in its payload and in the audit log.
   `offer` is refused without marketing consent, mints a single-use PERCENT
   code for the customer, sends as marketing with unsubscribe headers, and
   deactivates the code if the send fails. `review_request` uses the existing
   invite (stage 0, idempotent). Skips are reported, never faked as sent.
4. Fulfil / deliver / fail / resend, confirm payment / release hold / refund,
   and notes (with a customer-visible toggle) work from the page with the
   same roles the API enforces.
5. The orders list links every row to its page; the dashboard's recent
   orders too. The customers screen seeds its search from `?q=`.
6. `tsc`, eslint and prettier clean; `pnpm --filter @da/api test` green.
