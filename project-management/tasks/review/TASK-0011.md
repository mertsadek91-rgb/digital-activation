### What the fingerprint protects

- **One job only: stop the same licence being stored, and so sold, twice.** It is not used for rate limiting, visitor throttling or abuse detection (visitor ids use a separate daily `AnalyticsSalt`, TASK-0097).
- Computed in `apps/api/src/vault/kek.ts:220-222`: SHA-256 of `salt + NUL + trimmed plaintext`, where the salt is `process.env.VAULT_FINGERPRINT_SALT ?? ''` (line 221). Empty salt = plain SHA-256 of the key.
- Stored in `vault.LicenseKey.fingerprint`, `String @unique` (`packages/db/prisma/schema/30-vault.prisma:42`; index `LicenseKey_fingerprint_key`, `migrations/20260909120000_init/migration.sql:1155`).
- Checked in two places, both in `apps/api/src/vault/vault.service.ts`:
  - `importKeys` (bulk stock import): dedupes within the batch (line 127) and against the vault (lines 136-145); skipped rows are reported as duplicates.
  - `fulfilManually` (key pasted onto an order): refuses a key already in the vault or already delivered to another order (lines 308-321).
- Not used to decrypt, deliver or reveal anything. Encryption (KEK/DEK) is independent of the salt.

### What breaks if the salt changes

- Existing rows keep their old digest; new input is hashed with the new salt. The two never match, so **duplicate detection silently stops working against every pre-change row** — the unique index cannot catch it either, because the digests differ. A supplier re-sending a block, or staff pasting a key already in stock, would be accepted and the key could be sold twice.
- Nothing else breaks: no delivery, reveal or order flow reads the fingerprint.
- The rows are recoverable: every row can be decrypted under the vault role, so fingerprints can be **recomputed** with a new salt (no data is lost, no key needs re-importing). A recompute could also surface any genuine duplicates already stored (unique-index violation) — that is a finding, not a failure.

### Facts that shape the choice

- `config/env.ts` does not declare the variable and does not validate it; the production block (`env.ts:275-310`) refuses `KEK_PROVIDER=local`, `MAIL_TRANSPORT=capture` and placeholder secrets, but says nothing about the salt.
- Because it is not in the schema, the API **ignores the salt when it comes from the env file** and only sees it when the host injects it directly (BUG-0020; exemption at `apps/api/src/config/env-coverage.test.ts:18-19`). Coolify injects directly, so Coolify works; a local run against the same staging database would fingerprint with an empty salt. Mixed salts in one table are exactly the failure above.
- `.env.example:221-226` already documents "set it once"; the production-transition plan (`reports/release/TASK-0044-production-transition.md`, row D5) says the value must be carried unchanged and never rotated.
- Exposure is limited: the column lives in the `vault` schema, which the app role cannot read (BUG-0002 re-audit). The risk is a vault-role credential or a dump.
- Unknown to the repository (owner only): (1) is the salt set on the Coolify API resource; (2) how many `LicenseKey` rows exist on staging (legacy keys were not migrated, TASK-0043, but admin imports and manual fulfilment may have created some).

### Recommendation (analysis, not a decision)

**Option a.** The rows can be recomputed from the ciphertext, so the "breaking existing fingerprints" problem is a one-off, reviewable data step rather than a reason for a long-lived dual path — and at staging scale it is likely tiny or empty. Option b adds permanent-feeling complexity to the vault to avoid a step that a dry-run makes safe. Whatever is chosen, declare the variable in the env schema so the env file and Coolify cannot disagree (closes the BUG-0020 exemption).

### Operational steps (owner does these)

- If the salt is **not set**: generate a random value of at least 32 characters (e.g. `pnpm secrets:generate` or a password manager), set it on the Coolify API resource only, store it with the other production secrets, restart the API. Set it once; never rotate it without a recompute.
