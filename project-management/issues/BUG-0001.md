## Expected

A sweep takes its advisory lock, runs, and releases it, so the next tick on any connection can take it again.

## Actual

Each sweep calls `pg_try_advisory_lock` and later `pg_advisory_unlock` as two separate `$queryRaw` calls on the shared Prisma client. The client uses `@prisma/adapter-pg` with a connection pool (packages/db/src/index.ts:43), so the two calls can run on different connections. Session-level advisory locks belong to the connection that took them: the unlock on another connection returns false and the lock stays held by the first connection for as long as it lives in the pool. Later ticks that land on any other connection see `locked = false` and skip.

## Affected

fx-refresh, expire-drafts, **stranded-orders (fulfilment)**, referral-sweep, referral-expiry, cart-recovery, renewal-reminders, review-invites, back-in-stock — e.g. `apps/api/src/fulfillment/stranded-sweep.service.ts:45-51`, `apps/api/src/catalog/fx-refresh.service.ts:67-80`.

## Reproduction

Not yet reproduced at runtime; established by reading the code and Postgres semantics. TASK-0010 starts with a test against a real Postgres that proves or disproves it.

## Root cause

Session-scoped lock used through a pooled client with no connection affinity.
