## Facts (checked 2026-09-29)

- **One new-stack environment exists.**
  - Storefront: `new.digital-activation.com`
  - Admin: `admin.digital-activation.com`
  - API: `api.digital-activation.com`

  The staging storefront's CSP `connect-src` points at
  `api.digital-activation.com`. The admin and API hostnames are the production
  names in `docs/deployment.md`.

- **The API serves the database at the published port that the local `.env`
  uses.** Both show 71 published products.
- **That database holds demo records.** Five of six customers and four of five
  orders use `example.invalid`, the domain the `db:demo` script generates. One
  customer and one order use another domain.
- **The nine cron sweeps run on staging.** They are registered unconditionally
  (`app.module.ts:80`), so cart recovery, review invitations, renewals and
  back-in-stock all run. Only the FX refresh can be switched off.
- **Indexing is correctly off:** `noindex, nofollow`, and `robots.txt` says
  `Disallow: /`.

## Why it matters

This is not a vulnerability. It means **staging will become production in
place**. Unless the cutover removes them, these would all carry into production:

- demo orders and customers
- the admin account
- any test keys

The sweeps are already emailing whatever addresses the database holds.

## Remediation

- Add a cutover step that clears demo data (TASK-0044).
- Confirm which mail transport Coolify uses today (needs the owner's input).
